# 09 未来信件与业务规则

未来信件适合解释“为什么业务规则必须放后端”。

## 数据所有权

所有读写都先执行：

```java
Long userId = requireUserId(username);
FutureLetterEntity entity = futureLetterRepository
    .findByIdAndUserId(id, userId)
    .orElseThrow(() -> new ResponseStatusException(
        HttpStatus.NOT_FOUND, "未来信件不存在"));
```

`username` 来自 JWT Authentication，再映射到数据库主键。路径里的 `id` 只是信件 ID，必须与当前用户 ID 组合查询。

## 创建时的默认值

```java
new FutureLetterEntity(
    userId,
    request.title(),
    request.content(),
    request.mood(),
    request.openAt().atStartOfDay(),
    defaultValue(request.status(), "sealed"),
    defaultValue(request.visibility(), "private"),
    request.allowEditBeforeOpen() == null
        || request.allowEditBeforeOpen(),
    LocalDateTime.now()
);
```

- 日期通过 `atStartOfDay()` 转成当天零点。
- 未给状态时默认封存，未给可见性时默认私密。
- 包装类型 Boolean 可以区分“明确 false”和“没有传值”。

## 开启规则

```java
if ("draft".equals(entity.getStatus())) {
    throw new ResponseStatusException(
        HttpStatus.CONFLICT, "草稿需要先封存才能开启");
}
if (LocalDateTime.now().isBefore(entity.getOpenAt())) {
    throw new ResponseStatusException(
        HttpStatus.CONFLICT, "还没有到信件开启时间");
}
if (!"opened".equals(entity.getStatus())) {
    entity.setStatus("opened");
    entity = futureLetterRepository.save(entity);
}
```

返回 409 表示请求格式没有问题，但与当前资源状态冲突。重复开启已经打开的信件不会重复产生副作用，具有一定幂等性。

## 为什么前端禁用按钮还不够

用户可以修改浏览器脚本、伪造时间或直接调用 API。到期判断必须使用服务器时间并在 Service 再执行一次。前端判断仅用于提前提示，提高体验。

## 当前实现可改进点

- 状态和可见性当前使用字符串，可改为 Enum，并在 DTO 层限制合法取值。
- `update` 目前允许直接修改状态，应该进一步限制合法状态迁移。
- “封存后是否允许编辑”应在 update Service 中依据 `allowEditBeforeOpen` 和状态严格检查。
- 涉及多步状态写入时可增加 `@Transactional`，并考虑并发更新的乐观锁。

## 评委可能追问

**为什么规则放 Service 而不是 Controller？** Service 不依赖具体传输协议，可被 REST、定时任务或测试复用；Controller 只负责接收和返回 HTTP 数据。

**为什么不用前端当前时间？** 客户端时间可被修改且各设备不一致，权威业务时间应由服务器决定。
