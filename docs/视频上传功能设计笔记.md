## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 视频上传是不是"图片上传放大一下"？ | **不是**。它在 5 个维度发生质变，每个质变都牵出新知识（见第 1 节） |
| 以现在的架构最少要动哪几层？ | 5 处：① Nginx 体积/超时 ② Spring multipart 上限 ③ StorageService 新增视频通道 ④ UploadController/前端 新增视频入口 ⑤ 数据库加视频字段或新表 |
| 最容易踩的坑 | **大小限制是多层叠加的**（Nginx + Spring + Tomcat），任何一层没放开都表现为"上传失败但不知为何" |
| 最值钱的知识点 | **流式处理**（不要把视频读进 JVM 内存）、**预签名直传**（浏览器直传 MinIO）、**Range/206**（能拖进度条）、**跨系统一致性**（对象存储与数据库没有共同事务） |
| 最省事的规格建议 | 限制为**短视频 + H.264/MP4 + ≤30 秒 + ≤20MB**，可以完全绕开"转码"这个大坑（见第 7 节） |
| 20 Mbit/s 够用吗？ | 单人流媒体验：720p（2 Mbps）约 3 人同时观看、1080p（4 Mbps）约 2 人。演示够用，正式多人并发不够 |

## 1. 视频 ≠ 图片放大版：五个质变

| 质变 | 图片（项目现状） | 视频 | 由此引出的知识 |
| --- | --- | --- | --- |
| **体积** | 几百 KB ~ 5 MB | 几十 MB ~ 几百 MB | 流式处理、multipart 多层限制、超时、上传进度、断点续传 |
| **时间维度** | 静态，下载完才显示 | 有播放进度，要能拖动 | HTTP `Range` / `206 Partial Content`、`moov` 前置（faststart）、封面帧 |
| **编码多样** | jpg/png/webp 浏览器都能显示 | 手机直出可能是 HEVC/MOV，浏览器不一定能播 | 容器 vs 编码、转码、HLS、格式白名单 |
| **处理成本** | 近乎为零 | 抽帧/转码是 CPU 密集型 | 异步任务、状态机、任务队列 |
| **存储与流量成本** | 可忽略 | 显著（磁盘、流量费、备份体积） | 配额、生命周期、孤儿对象清理、成本核算 |

一句话记忆：**图片是"一个文件"，视频是"一段媒体资产"** —— 后者要管"能不能播、怎么播、存多久、谁在占带宽"。

## 2. 知识地图（按层，每层标注"你项目对应位置"）

### 2.1 HTTP / 传输层

**核心概念**
- `multipart/form-data` 的编码方式：一个请求体内分多个 part，视频通常占一个 part。
- **请求体大小限制是分层的**：浏览器 → Nginx → Tomcat → Spring。任何一层拒绝，现象都不同（Nginx 给 413、Spring 抛 `MaxUploadSizeExceededException`）。
- **超时**：上传大文件要同时考虑 `proxy_read_timeout`、连接超时、前端请求超时。
- **断点续传**：`Range` / `Content-Range` 请求头，或采用 **tus 协议**、**S3 Multipart Upload**。

**项目对应位置**
- `deploy/nginx-earth-online.conf`：`client_max_body_size 45m`、`/api/` 的 `proxy_read_timeout 90s`
- `backend/src/main/resources/application.yaml`：`spring.servlet.multipart.max-file-size: 5MB`、`max-request-size: 45MB`
- `web/src/api/httpClient.js`：统一的 fetch 封装（目前没有进度、没有超时、没有重试）

### 2.2 对象存储层（MinIO / S3 协议）

**核心概念**
- **对象键（object key）命名**：一个"媒体资产"通常占一个前缀，例如 `records/<user>/<uuid>/source.mp4 + poster.jpg + index.m3u8`。
- **分片上传（Multipart Upload）**：`CreateMultipartUpload → UploadPart → CompleteMultipartUpload`。大文件必须分片；分片还能并行加速、失败只重传某一片。
- **预签名直传（Presigned PUT）**：浏览器拿一个带签名的 URL，**直接传到 MinIO**，字节不经过 Spring Boot。需要给桶配置 **CORS**。
- **预签名下载（Presigned GET）+ 有效期**：项目已在用（图片 1 小时）。
- **Range 支持**：MinIO 原生支持 `206`，是"拖动进度条"的前提。
- **生命周期规则**：过期自动清理、冷数据转储。
- **桶策略**：私有桶 + 签名访问（项目已经是私有桶）。

**项目对应位置**
- `backend/src/main/java/com/earthonline/backend/storage/StorageService.java`：
  - `MAX_FILE_SIZE = 5MB`、`ALLOWED_CONTENT_TYPES = {image/jpeg,image/png,image/webp}`
  - `uploadImage()`：对象名 `folder/username/UUID.ext`，`putObject(stream(getInputStream(), size, -1L))`
  - `getPreviewUrl()`：预签名 GET，`.expiry(1, TimeUnit.HOURS)`，再把 host 换成 `MINIO_PUBLIC_URL`
- `deploy/nginx-earth-online.conf`：`location ^~ /earth-online-records/` 反代到 `127.0.0.1:9000`（图片/视频都是这条路径对外）

### 2.3 媒体格式与转码

**核心概念**
- **容器 vs 编码**：MP4(容器)/H.264(编码) 兼容性最好；WebM/VP9 体积小；AV1 更小但编码慢；iPhone 直出常是 HEVC(.mov/.mp4)，**部分浏览器不能播**。
- **`moov faststart`**：MP4 索引默认在文件尾部 → 必须下完才能播；`ffmpeg -movflags +faststart` 前置后才能边下边播。**点播必知**。
- **抽封面帧**：`ffmpeg -ss 1 -frames:v 1 poster.jpg`；也可以在前端用 `<video>` + `<canvas>` 抽（省服务器 CPU）。
- **HLS/DASH 切片**：`ffmpeg -hls_time 6` 生成 `.m3u8` + 分片，实现自适应码率与秒开。
- **算力现实**：转码耗时通常是片长的数倍；**2 核 4G 的 ECS 不适合在线转码**。

### 2.4 异步处理与状态机

**核心概念**
- "上传完成" ≠ "可播放"：抽帧/转码要异步做，于是需要**状态字段**：`uploading → processing → ready / failed`。
- 前端获取进度：轮询接口，或复用项目已有的 **WebSocket/STOMP** 推送。
- **幂等与重试**：同一任务重复执行不能产生两份资产；失败要能重试并最终落到 `failed`。
- 队列选型：轻量 `@Async` + 任务表；正式用 Redis Stream / RabbitMQ / Kafka。

### 2.5 数据库设计

**核心概念**
- 视频元数据比图片多：`object_key、mime、size、duration、width、height、poster_key、status、created_at`。
- **存对象键，不存预签名 URL**（URL 会过期）——项目图片已经是这个好习惯。
- **跨系统一致性**：写数据库和写对象存储**不是一个事务**。常见做法：
  1. 先传对象 → 再落库；落库失败要删对象（补偿）；
  2. 或用 `status=draft` + 定时清理孤儿对象；
  3. 不要试图用 `@Transactional` 去覆盖 MinIO 操作（这是分布式事务问题，不是本地事务）。

**项目对应位置**
- `backend/.../records/RecordEntity.java`：`@ElementCollection(fetch = EAGER) List<String> photos` → 子表 `record_photos(record_id, photo_url varchar(1000))`
- `backend/.../records/RecordService.java`：`validatePhotoObjectKeys()` 强制对象键前缀 `records/<username>/`
- `backend/.../futureletters/FutureLetterService.java`：`delete()` 只删数据库行（可对照理解"孤儿对象"问题）

### 2.6 前端（Vue）

**核心概念**
- **上传进度**：`fetch` **不支持**上传进度；要用 `XMLHttpRequest.upload.onprogress` 或 axios `onUploadProgress`（Element Plus `el-upload` 内部也是 XHR）。
- **不要整文件读进内存**：避免 `FileReader.readAsArrayBuffer()` 全量读视频；直接传 `File/Blob`。
- **分片**：`file.slice(start, end)` 切片、并发、失败重传、最后合并。
- **客户端预校验**：大小、MIME，以及**时长**（`video.duration` 必须等 `loadedmetadata` 事件才有值）。
- **客户端抽封面**：`<video>` seek 到某帧 → `canvas.drawImage` → `toBlob()` 得到 poster。
- **播放细节**：`<video controls poster preload="metadata" playsinline>`；移动端自动播放必须 `muted`；`object-fit`、点击再加载以省流量。
- **可取消/可恢复**：AbortController 取消；分片进度存 localStorage 支持刷新后续传。

**项目对应位置**
- `web/src/components/Profile/Timeline.vue`
  - `line 228`：`<input type="file" accept="image/jpeg,image/png,image/webp" multiple @change="handlePhotoSelect">`
  - `handlePhotoSelect()`：客户端校验（类型 + 5MB）→ `URL.createObjectURL(file)` 预览 → push `{preview, file, objectKey}`
  - `submitForm()`：遍历 `formData.photos`，未上传的先 `uploadRecordImage(photo.file)` 拿 `objectKey`，再随记录一起提交
  - 展示：`photo-grid` + `el-image`（详情弹窗里 `preview-teleported` 支持大图预览）
- `web/src/api/modules/uploads.js`：`uploadRecordImage / uploadAvatar / uploadChatImage`，均为 `FormData` + `request()`

### 2.7 后端（Spring Boot）

**核心概念**
- `MultipartFile` 的两种用法：`getBytes()`（**危险**，整段读进堆）vs `getInputStream()`（流式，安全）。
  > 项目现在用的是 `stream(file.getInputStream(), file.getSize(), -1L)` —— **已经是流式写法，这一点是加分项，答辩可以讲**。
- 临时文件与阈值：Tomcat/`commons-fileupload` 会把超过阈值的部分落盘，要关注磁盘与清理。
- 校验：**不能只信扩展名/`Content-Type`**，要做**文件头魔数嗅探**（MP4 的 `ftyp` box）。
- 事务边界：落库与对象存储分开处理（见 2.5）。
- 异步：`@Async`、`DeferredResult`，避免长上传占满 Tomcat 线程池。

### 2.8 安全、成本与运维

**安全**：MIME 伪装、路径穿越（object key 拼接）、越权播放（私有桶 + 签名）、防盗链、上传限流与配额、内容合规。
**成本**：
- 出口带宽（EIP 上限 = 并发观看能力上限）
- 流量费（按流量计费 ≈ 1 元/GB）
- 磁盘（视频是主要占用者）
- 备份体积（`mysqldump` 不受影响，但 MinIO 目录备份会变大）
**运维**：孤儿对象清理、上传失败率/处理耗时监控、容量告警。

## 4. 落地改造点（按层，只描述不实施）

### 4.1 配置层（最容易漏，也最容易出"玄学失败"）

| 文件 | 现状 | 视频场景需要 | 为什么 |
| --- | --- | --- | --- |
| `deploy/nginx-earth-online.conf` | `client_max_body_size 45m`；`/api/` `proxy_read_timeout 90s` | 提到 `100m`（或按你的上限）；上传接口 `proxy_read_timeout 300s` | 100MB 上传在慢网下远超 90 秒 |
| 同上（视频下载） | `^~ /earth-online-records/` 默认开启 `proxy_buffering` | 加 `proxy_buffering off;`（可再加 `proxy_max_temp_file_size 0;`） | 否则 Nginx 会把大文件先缓冲到磁盘，拖慢首帧、白占磁盘 |
| `application.yaml` | `max-file-size: 5MB`、`max-request-size: 45MB` | 例如 `max-file-size: 100MB`、`max-request-size: 200MB` | Spring 层同样会拒绝 |
| Tomcat（可选） | 默认 | 关注 `maxSwallowSize`、连接超时 | 上传被拒时能优雅收尾 |
| MinIO 桶 | 私有桶 | 若改为**直传**，需配置**桶 CORS**（允许站点 Origin 的 PUT） | 浏览器直传必须过 CORS |

### 4.2 后端改造点

| 文件 | 需要新增/调整 | 关键注意点 |

### 4.3 前端改造点

| 文件 | 需要新增/调整 | 关键注意点 |
| --- | --- | --- |
| `api/modules/uploads.js` | 新增 `uploadRecordVideo(file, onProgress)` | 想要进度必须换 **XHR**（fetch 无上传进度） |
| `components/Profile/Timeline.vue` | 表单新增视频选择入口；`accept="video/mp4,video/webm"`；预览用 `<video controls poster>`；提交时带 `videoObjectKey` | 单个视频即可，不要做"9 个视频"的多选 |
| 同上（展示） | 时间线卡片：视频显示**封面 + 播放按钮**（点击再加载），不要自动播放 | 省流量、省带宽 |
| 同上（详情弹窗） | 视频用 `<video controls>` 或简易播放器，占满宽度、限制最大高度 | 与图片的 `el-image` 分支并列 |

### 4.4 数据库改造点（两选一）

**方案 A：只存一个 key（最小改动）**

```
records 表新增列：video_key varchar(1000), video_poster_key varchar(1000), video_duration int
```
优点：改动小；缺点：多视频/多附件就要再加列，扩展性差。

**方案 B：独立媒体表（推荐）**

```
record_media(
  id, record_id, media_type('IMAGE'|'VIDEO'),
  object_key, poster_key, mime, size_bytes,
  duration_ms, width, height, status, created_at
)
```
优点：一套结构同时承载图片与视频，元数据有地方放，`status` 支撑异步处理；
代价：要把现有 `record_photos` 的数据迁移过来（可写一次性迁移脚本）。

> 注意：`ddl-auto: update` 能自动加表加列，但**改列类型/迁移数据不行**——正式项目应上 Flyway/Liquibase（这也是答辩可以提的改进点）。

## 5. 四个关键设计决策（含推荐）

| 决策 | 选项一 | 选项二 | 推荐 |
| --- | --- | --- | --- |
| **字节怎么走** | 浏览器 → Spring Boot → MinIO（现状） | 浏览器 →（预签名 PUT）→ MinIO **直传** | 视频选**直传**：后端完全不碰字节，省内存省线程；代价是桶要开 CORS、落库顺序要处理 |
| **同步还是异步** | 上传即完成（无转码） | 上传后异步抽帧/转码 + `status` | 先做**同步 + 客户端抽封面**（零服务器成本）；真需要转码再上异步 |
| **要不要转码** | 不转码，只做格式白名单 | 服务端 ffmpeg 转 H.264 / HLS | 演示阶段**不转码**，用"规格限制"替代（见第 7 节） |
| **单文件还是分片** | 一次 PUT（≤ 几十 MB） | 分片上传 / 断点续传 | ≤20MB 用单文件；要支持大文件再上分片 |

**一句话**：视频这条路，**"不让后端碰字节 + 限制规格 + 前端抽封面"** 是性价比最高的组合。

## 6. 分级路线图（L0 → L3，按投入递增）

### L0 最小可用（半天量级，不动架构）

**目标**：能上传一段短视频并在时间线里播放。

需要动的点：
1. `application.yaml`：`max-file-size` → `20MB`、`max-request-size` → `60MB`
2. `nginx-earth-online.conf`：`client_max_body_size 100m`（或 ≥ 规格上限）；`/api/` 超时放宽
3. `StorageService`：新增视频白名单（`video/mp4`、`video/webm`）+ `MAX_VIDEO_SIZE` + `uploadRecordVideo()`；`getExtension` 按 MIME 归一化
4. `UploadController`：新增 `POST /api/uploads/videos`
5. `uploads.js` + `Timeline.vue`：视频选择、`<video controls poster>` 预览、提交带 `videoObjectKey`
6. 数据库：方案 A（加 3 个列）即可

**验收方式**：上传 15MB 的 MP4 → 记录保存 → 时间线能播 → 拖动进度条能跳转 → 超限时前端给出明确提示。

**风险**：只信 `Content-Type` 会被伪装文件绕过（L1 补魔数校验）。

### L1 体验补齐（1~2 天）

- 上传**进度条**（换 XHR）、可取消、失败重试
- **客户端抽封面** + `poster` 占位；列表里点击再加载（省流量）
- **文件头魔数校验**（`ftyp` box）+ 时长上限（前端 `loadedmetadata` 校验，后端可选 ffprobe）
- 删除记录时**同步删除 MinIO 对象**（含图片，解决历史遗留的孤儿对象）

**验收**：手机上能看到百分比进度；封面先出现；刷新后视频仍在；删记录后 MinIO 里对象也没了。

### L2 架构升级（3~5 天）

- **预签名直传**：后端只发"签名 + 对象键"，浏览器直传 MinIO（桶 CORS）
- `status` 状态机（`uploading/processing/ready/failed`）+ 进度可查询
- **异步抽帧/转码**（`@Async` 或轻量队列；注意 2C4G 算力）
- 播放端：确认 `Range/206` 正常（若走自定义代理则需要手动支持）

**验收**：上传 100MB 文件时后端内存平稳（不 OOM）；大文件下载能拖进度；转码任务失败可重试。

### L3 进阶（按需，演示项目通常不需要）

- **分片上传 / 断点续传**（S3 Multipart 或 tus）
- **HLS 切片**（自适应码率、秒开）+ CDN
- 上传配额、内容合规扫描、监控告警面板

## 7. 规格与容量建议（按 20 Mbit/s 重算）

### 7.1 播放等待时间（服务器出口 20 Mbit/s ≈ 2.5 MB/s，实际按 2.2 MB/s 估）

| 视频规格 | 典型码率 | 30 秒体积 | 20 Mbit/s 下加载等待 | 5 Mbit/s 下（原配置） |
| --- | --- | --- | --- | --- |
| 480p | 0.8 Mbps | ≈ 3 MB | ≈ 1.4 s | ≈ 5.5 s |
| 720p | 2 Mbps | ≈ 7.5 MB | ≈ 3.4 s | ≈ 13.6 s |
| 1080p | 4 Mbps | ≈ 15 MB | ≈ 6.8 s | ≈ 27 s |
| 1080p 高码率 | 8 Mbps | ≈ 30 MB | ≈ 13.6 s | ≈ 55 s |
| 手机直出 4K | ~40 Mbps | ≈ 150 MB | ≈ 68 s | ❌ 不可用 |

**结论**：20 Mbit/s 让"720p / 30 秒 / 约 7MB"成为舒适档；**建议规格上限：≤30 秒、≤20MB、H.264 + MP4**。
（顺带对比：之前那张 3.44MB 的图片，5 Mbit/s 要 5.5 秒、20 Mbit/s 只要 1.4 秒 —— 带宽升级对图片同样有收益。）

### 7.2 并发能力

| 同时观看人数 | 720p（2 Mbps） | 1080p（4 Mbps） |
| --- | --- | --- |
| 1 人 | ✅ 流畅 | ✅ 流畅 |
| 3 人 | ✅ 接近打满 | ⚠️ 开始卡 |
| 5 人以上 | ❌ 明显卡顿 | ❌ 不可用 |

> 出口带宽是**所有人共享**的：答辩时如果评委和你在不同设备同时看视频，会互相抢带宽。演示前可以先只留一个视频源。

### 7.3 磁盘与费用

| 项目 | 估算 |
| --- | --- |
| 单条 15MB 视频 | 40GB 磁盘理论上可存 2000+ 条，但要给 MySQL/MinIO/图片留余量 |
| 建议配额 | 每用户视频总量 ≤ 500MB 或条数 ≤ 50（后端校验 + 前端提示） |
| 流量费（按流量计费 ≈1 元/GB） | 一次 15MB 播放 ≈ **1.5 分钱**；演示几十次不到 1 元 |

## 9. 答辩问答（可以直接背）

**Q1：视频上传和图片上传最大的区别是什么？**
> 体积和时间维度带来的连锁反应。图片是"一个静态文件"；视频是"一段媒体资产"：它需要能边下边播（`moov` faststart + `Range/206`）、可能需要转码（浏览器不一定支持手机直出的 HEVC）、元数据更多（时长/宽高/封面），因此还要引入异步状态机。所以我先把规格限制住，而不是一上来就做转码。

**Q2：为什么不能把视频读成一个 byte 数组再上传？**
> `MultipartFile.getBytes()` 会把整个文件读进 JVM 堆，100MB 视频几个并发就 OOM。正确做法是**流式**：`putObject(stream(file.getInputStream(), file.getSize(), -1L))`（项目现有的图片上传就是这么写的），或者更进一步用**预签名直传**，让字节根本不经过后端。

**Q3：为什么上传限制要在 Nginx 和 Spring 两处都配？**
> 请求先经过 Nginx 再进 Spring，任何一层都可以拒绝。Nginx 拒绝时返回 413 且请求体根本没到后端；Spring 拒绝时会在应用日志里抛 `MaxUploadSizeExceededException`。**排查时要先看是哪一层拒的**，否则会出现"后端没日志、前端只报失败"的困惑。

**Q4：视频为什么需要 Range 请求？**
> 拖动进度条和边下边播都依赖 `Range: bytes=…`，服务端要回 `206 Partial Content`。MinIO 原生支持；如果中间加了自己的代理，就必须保证 Range 头被转发、响应码不被改写。

**Q5：数据库和 MinIO 怎么保证一致？**
> 它们没有共同事务。我的做法是"先上传对象、再落库"，落库失败就删对象做补偿；同时用 `status` 字段标记处理中的资产，配合定时任务清理孤儿对象。**不能用 `@Transactional` 假装它们是同一个事务**。

**Q6：为什么不直接做 HLS + CDN？**
> 因为现在的场景是"个人记录里的短视频"，切片和 CDN 的复杂度与成本明显超过收益。我按"规格限制（≤30 秒 / ≤20MB / MP4）→ 预签名直传 → 客户端抽封面"这个顺序做，把复杂度留给真正需要的时候。

## 11. 一页速记

- **五个质变**：体积、时间维度、编码、处理成本、存储流量成本
- **四件最值钱的事**：流式处理、预签名直传、Range/206、跨系统一致性
- **三层限制**：Nginx `client_max_body_size` + Spring `multipart` + 前端校验
- **两个不要**：不要把视频读进内存；不要用 `@Transactional` 假装对象存储和数据库是同一个事务
- **一个建议**：先把规格限制成"≤30 秒 / ≤20MB / H.264+MP4"，能绕开转码这个最大的坑
