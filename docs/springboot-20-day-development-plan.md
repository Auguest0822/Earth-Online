# Earth Online：Spring Boot 后端 20 天开发计划

> 可用时间：20 天 × 6 小时/天，共约 120 小时  
> 当前状态：Vue 3 前端主体已经完成，业务数据仍以 Mock/localStorage 为主；现有新闻服务是 Node.js 演示实现  
> 本阶段目标：完成一个能够注册登录、保存个人数据、运行核心业务、展示新闻并可部署演示的全栈项目

## 1. 现在是否应该建立后端

**是。接下来应立即建立 Spring Boot 后端。**

目前前端已经有页面和 API 请求封装，继续增加前端页面的收益不高。项目真正缺少的是：

- 用户身份认证；
- 数据库持久化；
- 业务数据的用户隔离；
- 统一的错误处理和参数校验；
- 前后端真实联调；
- 可部署、可演示的完整运行链路。

前端已经预留了以下接口模块，可以直接作为后端开发清单：

- `web/src/api/modules/auth.js`：注册、登录、当前用户；
- `web/src/api/modules/profile.js`：个人资料、头像；
- `web/src/api/modules/records.js`：时间记录；
- `web/src/api/modules/futureLetters.js`：未来信件/时间胶囊；
- `web/src/api/modules/tags.js`：标签；
- `web/src/api/modules/stats.js`：首页和年度统计；
- `web/src/api/newsService.js`：新闻数据。

因此本阶段不是从零设计功能，而是让已有前端逐步连接真实后端。

## 2. 20 天后的交付标准

### 必须完成（MVP）

- Spring Boot 项目能够独立启动；
- MySQL 数据库和表结构可自动初始化；
- 用户能够注册、登录和获取当前用户；
- JWT 能保护需要登录的接口；
- 用户能够查看和修改个人资料；
- 用户能够新增、修改、删除自己的时间记录；
- 用户能够创建、修改、删除和开启未来信件；
- 首页统计和年度统计来自真实数据库；
- “地球动态”能够从后端获取新闻；
- 前后端联调完成，核心页面不再依赖 Mock；
- 有基本测试、接口文档、启动说明和演示数据；
- 项目能够通过一个明确步骤启动，最好能够部署演示。

### 有余力再做（加分项）

- 头像文件上传；
- 新闻定时采集和数据库缓存；
- Docker Compose 一键启动；
- 基于记录数据生成简单年度总结；
- Swagger/OpenAPI 在线接口文档；
- Actuator 健康检查。

### 本阶段明确不做

- 新闻 SSE/WebSocket/Web Push 实时推送；
- 通用网页爬虫；
- 复杂 AI 推荐或向量数据库；
- 完整好友/社交系统；
- 微服务、Kafka、分布式事务；
- 复杂 RBAC 权限管理；
- 为追求“架构完整”而提前引入 Redis。

这些功能会明显扩大范围。20 天内应优先保证主流程完整、稳定、能讲清楚。

## 3. 推荐技术栈

### 后端

- Java 21 LTS（如果本机环境不方便，也可以使用 Java 17）；
- Spring Boot 3.x；
- Maven；
- Spring Web；
- Spring Validation；
- Spring Data JPA；
- Spring Security；
- JWT；
- MySQL 8；
- Flyway 数据库迁移；
- Springdoc OpenAPI（可选但推荐）；
- JUnit 5 + Spring Boot Test。

### 为什么建议 Spring Data JPA

这个项目的数据关系比较直观，且开发时间有限。JPA 可以减少普通 CRUD 的代码量，让时间集中在认证、业务规则和联调上。

如果学习目标明确要求 MyBatis，也可以使用 MyBatis-Plus，但不要同时使用 JPA 和 MyBatis-Plus，以免增加学习和维护成本。

### 工程目录建议

在仓库中新建独立目录：

```text
backend/
├─ pom.xml
├─ src/main/java/.../earthonline/
│  ├─ config/
│  ├─ common/
│  ├─ auth/
│  ├─ user/
│  ├─ record/
│  ├─ tag/
│  ├─ capsule/
│  ├─ stats/
│  └─ news/
├─ src/main/resources/
│  ├─ application.yml
│  ├─ application-dev.yml
│  └─ db/migration/
└─ src/test/java/
```

推荐按业务模块组织，而不是把所有 Controller、Service、Repository 分别堆在三个大目录中。

现有 `server/` 暂时保留，作为新闻接口的参考实现。等 Spring Boot 新闻接口达到相同能力并且前端切换成功后，再决定是否删除；本计划不要求立即删除旧代码。

## 4. 数据模型建议

第一版只建立支持核心业务的表：

### User

- `id`
- `username`，唯一；
- `password_hash`；
- `nickname`；
- `avatar_url`；
- `bio`；
- `created_at`、`updated_at`。

### Record（个人时间记录）

- `id`；
- `user_id`；
- `title`；
- `content`；
- `event_date`；
- `mood`；
- `location`；
- `created_at`、`updated_at`。

### Tag 与 RecordTag

- 标签属于用户；
- 记录与标签为多对多关系；
- 同一用户的标签名称应唯一。

### FutureLetter（未来信件/时间胶囊）

- `id`；
- `user_id`；
- `title`；
- `content`；
- `open_at`；
- `status`：`SEALED`、`OPENED`；
- `opened_at`；
- `created_at`、`updated_at`。

第一版的“到期发送”可以简化为“到达时间后允许用户开启”。真正的邮件或消息推送留到以后。

### News（可选持久化）

- `id`；
- `source`；
- `source_url`，唯一；
- `title`；
- `summary`；
- `image_url`；
- `category`；
- `region`；
- `published_at`；
- `collected_at`。

新闻表不是前 10 天的阻塞项。如果进度落后，可以先让 Spring Boot 代理/聚合 GDELT，再把新闻入库留到后续。

## 5. API 优先级

### P0：必须完成

```http
POST   /api/auth/register
POST   /api/auth/login
GET    /api/auth/me

GET    /api/profile
PATCH  /api/profile

GET    /api/records
GET    /api/records/{id}
POST   /api/records
PATCH  /api/records/{id}
DELETE /api/records/{id}

GET    /api/future-letters
GET    /api/future-letters/{id}
POST   /api/future-letters
PATCH  /api/future-letters/{id}
DELETE /api/future-letters/{id}
POST   /api/future-letters/{id}/open

GET    /api/stats/dashboard
GET    /api/stats/yearly?year=2026

GET    /api/news?category=all
GET    /api/health
```

### P1：时间允许时完成

```http
POST   /api/profile/avatar
GET    /api/tags
POST   /api/tags
DELETE /api/tags/{id}
POST   /api/ai/yearly-summary
```

所有用户业务接口必须从 JWT 中取得当前用户 ID，不能相信前端传入的 `userId`。查询、修改和删除时都必须附带当前用户条件，防止访问其他用户的数据。

## 6. 每天 6 小时的时间使用方式

建议每天固定划分：

```text
0.5 小时：回顾昨天、确定当天验收目标
1.0 小时：学习当天必需知识
3.5 小时：编码和前后端联调
0.5 小时：测试、修复
0.5 小时：提交代码、记录问题和更新文档
```

不要先连续学习几天再编码。每天只学习完成当天功能所需的知识，并立即落地。

## 7. 20 天详细安排

## 第 1 阶段：后端基础与认证（第 1～4 天，24 小时）

### 第 1 天：冻结范围，建立 Spring Boot 工程

学习重点：Spring Boot 项目结构、依赖注入、Controller。

任务：

- 确认上述 MVP，不再增加新页面；
- 创建 `backend/` Maven 项目；
- 加入 Web、Validation、JPA、MySQL、Security、Flyway；
- 配置 `application-dev.yml` 和环境变量；
- 实现 `/api/health`；
- 配置前端开发代理或后端 CORS；
- 建立统一 Git 提交习惯。

当天验收：Spring Boot 和 Vue 能同时启动，浏览器能请求 `/api/health`。

### 第 2 天：数据库与基础工程规范

学习重点：JPA Entity、Repository、Flyway、DTO。

任务：

- 创建 MySQL 开发数据库；
- 编写第一份 Flyway 迁移；
- 建立 User 表和实体；
- 定义统一响应约定；
- 实现业务异常、全局异常处理；
- 实现参数校验错误返回；
- 配置日期和 JSON 序列化。

当天验收：应用启动时自动建表；错误请求能返回统一、可读的 JSON。

### 第 3 天：注册与登录

学习重点：密码哈希、JWT 基础、Spring Security 过滤链。

任务：

- 使用 BCrypt 保存密码；
- 实现注册接口和用户名唯一校验；
- 实现登录接口；
- 签发 access token；
- 实现 JWT 解析过滤器；
- 配置公开接口与受保护接口。

当天验收：Postman/Apifox 可以完成注册、登录；错误密码不能登录；数据库中没有明文密码。

### 第 4 天：当前用户与前端登录联调

学习重点：SecurityContext、前端 token 请求流程、路由守卫。

任务：

- 实现 `/api/auth/me`；
- 对齐前端期望的登录返回结构；
- 联调 `auth.js` 和 `LoginView.vue`；
- 为受保护页面增加路由守卫；
- 处理 401：清理 token 并跳回登录页；
- 补充认证接口测试。

当天验收：网页完成真实注册、登录、刷新后恢复登录状态和退出登录。

## 第 2 阶段：核心个人数据（第 5～10 天，36 小时）

### 第 5 天：个人资料

学习重点：DTO 映射、部分更新、用户数据隔离。

任务：

- 实现查询个人资料；
- 实现昵称、签名等资料修改；
- 对齐 `profile.js` 返回字段；
- 联调个人主页；
- 头像先支持 URL，文件上传可延后。

当天验收：修改资料后刷新页面，数据仍然存在。

### 第 6 天：时间记录 CRUD（一）

学习重点：实体关联、分页、排序。

任务：

- 建立 Record 表、Entity、Repository；
- 实现记录列表、详情和新增；
- 默认按事件时间倒序；
- 接口从当前登录用户取得 `userId`；
- 支持基础分页参数。

当天验收：两个测试用户只能看到自己的记录。

### 第 7 天：时间记录 CRUD（二）与前端联调

任务：

- 实现记录修改和删除；
- 校验记录归属权；
- 对齐前端字段和日期格式；
- 联调首页、时间轴、个人页面；
- 修复新增、编辑、删除后的状态刷新；
- 补 CRUD 测试。

当天验收：时间记录完整闭环可用，刷新页面不会丢失。

### 第 8 天：标签功能

学习重点：数据库多对多关系、唯一约束。

任务：

- 建立 Tag 和 RecordTag；
- 实现标签列表、新增、删除；
- 记录新增/修改时关联标签；
- 防止删除仍被使用的标签，或明确采用解除关联策略；
- 联调标签展示。

当天验收：用户可以为记录添加标签，并按用户正确隔离。

如果当天进度落后，可以暂时把标签保存成 Record 的简单字符串字段，先保证核心流程。

### 第 9 天：未来信件 CRUD

学习重点：状态枚举、时间校验、业务规则放置位置。

任务：

- 建立 FutureLetter 表；
- 实现列表、详情、新增、修改和删除；
- 校验开启时间必须晚于创建时间；
- 已开启信件不能重新密封；
- 已过开启时间不等于自动开启。

当天验收：未来信件可以保存，状态和时间规则正确。

### 第 10 天：开启未来信件并联调时间胶囊页面

任务：

- 实现 `/future-letters/{id}/open`；
- 只有到达 `openAt` 才能开启；
- 防止重复开启；
- 联调 `CapsuleView.vue`；
- 测试未到期、已到期、已开启和越权四种情况；
- 完成本阶段代码整理。

当天验收：时间胶囊主流程通过网页完整演示。

## 第 3 阶段：统计、新闻与整体联调（第 11～15 天，30 小时）

### 第 11 天：首页统计接口

学习重点：聚合查询、DTO 组装。

任务：

- 盘点首页实际使用的统计字段；
- 实现记录总数、时间胶囊数量、近期记录等统计；
- 尽量使用数据库聚合查询，避免查询全部数据后在 Java 中统计；
- 联调首页卡片。

当天验收：首页核心数据来自当前用户的真实数据库记录。

### 第 12 天：年度统计

任务：

- 实现 `/stats/yearly?year=...`；
- 统计月度记录数量、心情分布、标签分布等现有页面需要的数据；
- 处理没有数据的年份；
- 联调 ECharts 和年度页面；
- 检查时区和年份边界。

当天验收：切换年份后图表显示正确，无数据时页面不报错。

### 第 13 天：新闻模块迁移设计与基础实现

学习重点：Spring `RestClient`/`WebClient`、第三方 API、超时和降级。

任务：

- 阅读现有 `server/news-server.js`；
- 在 Spring Boot 中定义统一 News DTO；
- 接入 GDELT；
- 配置连接和读取超时；
- 实现简单字段标准化、分类和去重；
- 保留本地 fallback 数据。

当天验收：Spring Boot `/api/news` 可以独立返回统一新闻数据。

### 第 14 天：新闻缓存与前端切换

任务：

- 使用内存缓存或 Spring Cache，缓存 10 分钟；
- 可选接入 NewsAPI，密钥只放后端环境变量；
- 对齐现有 `newsService.js` 返回结构；
- 将前端新闻请求切换到 Spring Boot；
- 验证分类、外部接口失败和 fallback 模式。

当天验收：“地球动态”不再依赖 Node 新闻服务也能运行。

如果进度落后，不要在这一天实现新闻数据库和实时推送。缓存版本已经足够作为本期成果。

### 第 15 天：全站退出 Mock 模式

任务：

- 将 `VITE_APP_DATA_SOURCE` 切换为 API；
- 从登录开始逐页回归；
- 清理字段命名不一致；
- 统一日期、分页和错误提示；
- 修复刷新页面、直接访问路由、token 过期等问题；
- 整理未实现入口，必要时显示“开发中”。

当天验收：主要演示路径不需要手动切回 Mock。

## 第 4 阶段：质量、部署与交付（第 16～20 天，30 小时）

### 第 16 天：安全与边界检查

### 第 17 天：自动化测试

学习重点：JUnit 5、MockMvc、Service 测试。

任务：

- 为注册、登录编写测试；

不要追求很高的覆盖率数字。优先覆盖认证、数据归属权和时间胶囊状态规则。

### 第 18 天：数据库迁移、演示数据与文档

任务：

- 更新根 README 的技术栈、启动方式和目录结构。

当天验收：另一台电脑按照 README 能完成环境配置和启动。

### 第 19 天：部署或一键启动

优先方案：

- 如果有可用服务器：部署前端、Spring Boot 和 MySQL；

任务：

- 配置反向代理或统一 API 地址；
- 验证生产环境 CORS、刷新路由和数据库连接；
- 记录部署步骤和已知限制。

当天验收：获得一个可访问地址，或者在干净环境中一条明确流程即可启动。

### 第 20 天：最终回归与项目表达

任务：

- 按真实用户路径进行完整回归；
- 只修复阻塞演示的问题，不再开发新功能；
- 准备 3～5 分钟演示流程；
- 绘制一张简单架构图和数据库关系图；
- 整理项目亮点、难点、问题和后续计划；
- 打版本标签或建立最终提交。

推荐演示顺序：

```text
注册/登录
→ 修改个人资料
→ 新建一条时间记录
→ 查看时间轴与统计变化
→ 创建并查看时间胶囊
→ 查看地球动态新闻
→ 展示接口文档和数据库
```

当天验收：项目能够稳定演示，README、接口说明和后续规划完整。

## 8. 每 5 天的里程碑

| 测试、部署和文档 | 24 小时 | 20% |
| 机动缓冲 | 6 小时 | 5% |

第 15 天以后不要再改变数据库核心设计或引入新的大型框架。若任务延误，应按以下顺序删除：

1. AI 年度总结；
2. 头像文件上传；
3. 新闻入库与定时采集；
4. 标签多对多；
5. Docker 和在线部署。

不能删除的部分是认证、用户数据隔离、时间记录、未来信件、基本统计和文档。

## 10. 每个功能的完成定义

一个功能只有同时满足以下条件才算完成：

- 数据库迁移已经提交；
- 后端接口可以正常调用；
- 参数校验和主要异常已经处理；
- 当前用户不能访问其他用户数据；
- 前端已经连接真实接口；
- 页面刷新后数据仍存在；
- 至少完成关键路径测试；
- README 或接口文档已经更新。

仅完成 Controller，或者仅在 Postman 中调用成功，都不算完整完成。

## 12. 本阶段结束后的路线

20 天版本完成后，再按以下顺序继续扩展：

1. 新闻数据库持久化和定时采集；
2. SSE 页面实时更新；
3. 通知中心和 Web Push；
4. 好友关系和互动动态；
5. AI 年度总结、内容分类或推荐；
6. Redis 缓存和任务队列；
7. 更完整的自动化部署与监控。

新闻实时更新的详细方案见 `docs/news-realtime-update-plan.md`。

## 13. 最重要的执行原则

- 每天完成一个可以验证的小闭环；
- 先实现业务正确性，再优化架构；
- 先连接真实数据库，再添加新页面；
- 不在 20 天内学习和引入不必要的中间件；
- 第 15 天以后以修复、测试、部署和表达为主；
- 项目完整可运行，比功能数量多更重要。
