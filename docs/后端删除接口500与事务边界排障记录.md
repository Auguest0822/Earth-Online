# 事记删除接口 500 与事务边界排障记录

> 记录日期：2026-09-12  
> 适用项目：Earth Online（Vue 3 + Spring Boot 4 / Spring Data JPA + MySQL）  
> 涉及文件：`RecordService.java`、`RecordRepository.java`、`RecordEntity.java`、`GlobalExceptionHandler.java`、`web/src/components/Profile/Timeline.vue`  
> 相关文档：[`chat-realtime-websocket-troubleshooting.md`](./chat-realtime-websocket-troubleshooting.md)（实时聊天排障）、[`华为云服务器更新部署指南.md`](./华为云服务器更新部署指南.md)

## 0. 结论速览

公网上删除时间线里的事记时报错，页面弹出红色提示：**“后台服务暂时不可用，请稍后重试”**，而且**刷新后记录还在**——即“报错 + 没删掉”。

根因只有一句话：**`RecordService.delete()` 没有 `@Transactional`，而它调用的派生删除方法 `deleteByIdAndUserId` 不像 `save()` 那样自带事务**。没有事务，Hibernate 只是把实体标记为“待删除”，一条 SQL 都没发；等请求结束关闭 `EntityManager` 时才去 flush，此时没有事务 → 抛 `TransactionRequiredException` → 全局异常处理器返回 500，记录自然没删掉。

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| `DELETE /api/records/{id}` 返回 500，记录仍在 | 删除走的是**派生删除方法**，它不自带事务；Service 层也没声明事务 | Service 类加 `@Transactional(readOnly = true)`，写操作（create/update/delete）各加 `@Transactional` |
| 只有删除坏，增、改、查都正常 | `save()` / 查询方法是 `SimpleJpaRepository` 自带 `@Transactional` 的方法 | 同上 |
| 日志里查不到任何异常堆栈 | `GlobalExceptionHandler` 捕获 `Exception` 后**不记录任何日志** | 5xx 记 ERROR（含堆栈）、4xx 记 WARN、校验失败记 WARN |

## 2. 排查过程

修好日志之后（见第 4 节），还需要把**事务行为**看清楚，于是本地用带事务日志的方式启动后端复现：

```bash
java -jar backend/target/backend-0.0.1-SNAPSHOT.jar --server.port=8081 \
  --logging.level.org.springframework.transaction.interceptor=TRACE \
  --logging.level.org.springframework.orm.jpa=DEBUG
```

再一次执行删除，日志给出了决定性证据：

```text
TRACE TransactionInterceptor : No need to create transaction for
       [org.springframework.data.jpa.repository.support.SimpleJpaRepository.deleteByIdAndUserId]:
       This method is not transactional.                    ← ① 删除没有事务
Hibernate:
    select re1_0.id, re1_0.content, ... from records re1_0
    where re1_0.id=? and re1_0.user_id=?                    ← ② 先查实体（准备 em.remove）
Hibernate:
    select p1_0.record_id, p1_0.photo_url from record_photos p1_0 where p1_0.record_id=?
Hibernate:
    select k1_0.record_id, k1_0.keyword from record_keywords k1_0 where k1_0.record_id=?
DEBUG OpenEntityManagerInViewInterceptor : Closing JPA EntityManager
                                                            ← ③ 全程没有一条 DELETE 语句
```

对照同一批日志里**新增/修改**的部分：

```text
DEBUG JpaTransactionManager : Creating new transaction with name
       [org.springframework.data.jpa.repository.support.SimpleJpaRepository.save]
TRACE TransactionInterceptor : Getting transaction for [...SimpleJpaRepository.save]
Hibernate: insert into records (...) values (...)           ← 真的执行了
DEBUG JpaTransactionManager : Committing JPA transaction on EntityManager
```

**同样是 repository 方法，`save()` 自己开事务、真的落库；`deleteByIdAndUserId` 没有事务、什么都没发。** 这就是“只有删除坏”的原因。

### 2.1 顺带确认的数据结构

```sql
SHOW CREATE TABLE record_photos\G
```

```sql
CREATE TABLE `record_photos` (
  `record_id` bigint NOT NULL,
  `photo_url` varchar(1000) ...,
  KEY `FK9o409r7fxlgfxj8aayapa0ibx` (`record_id`),
  CONSTRAINT `FK9o409r7fxlgfxj8aayapa0ibx`
    FOREIGN KEY (`record_id`) REFERENCES `records` (`id`)      -- 外键，且没有 ON DELETE CASCADE
)
```

`record_keywords` 同样如此。也就是说：

- 删除一条事记，必须**先删子表再删主表**（否则外键报错）；
- Hibernate 只有在**一个事务内**才会按这个顺序把 SQL 发出去。

## 3. 根因

### 3.1 为什么派生删除方法“没有事务”

在 Spring Data JPA 里，两类方法的待遇不一样：

| 方法来源 | 例子 | 是否自带事务 |
| --- | --- | --- |
| `SimpleJpaRepository` 的内置方法 | `save()`、`delete(entity)`、`deleteById()` | ✅ 方法上带 `@Transactional`，会自己开事务 |
| 我们自己在接口里声明的**派生方法** | `deleteByIdAndUserId(id, userId)` | ❌ 只是生成的 JPQL 查询执行，不会继承内置方法的 `@Transactional` |

而 Service 层当时**没有声明事务**，于是派生删除就在“无事务”的状态下执行。

### 3.2 完整因果链

```text
RecordService.delete() 没有 @Transactional
      ↓
deleteByIdAndUserId() 先查出实体，再调用 em.remove(entity)
      ↓
没有事务 → Hibernate 不会 flush，一条 DELETE 都不发
      ↓
请求结束，OpenEntityManagerInViewInterceptor 关闭 EntityManager
      ↓
关闭时才尝试 flush 挂起的 remove，此时没有事务
      ↓
抛 TransactionRequiredException
      ↓
GlobalExceptionHandler 捕获 → 返回 500（且当时不写日志）
      ↓
前端提示“后台服务暂时不可用，请稍后重试”，数据库里的记录完全没变
```

顺带解释一个容易困惑的点：**为什么异常是在“关闭 EntityManager”时才抛？** 因为项目默认开启 `spring.jpa.open-in-view=true`（启动日志里也有这条 WARN），EntityManager 的生命周期被拉长到整个请求。挂起的删除因此一直没被发现，直到请求收尾。

### 3.3 修复

文件：`backend/src/main/java/com/earthonline/backend/records/RecordService.java`

```java
/**
 * 事记的增删改查。
 *
 * 注意：整个类必须有事务边界。`save()` 是 Spring Data 自带 @Transactional 的方法，
 * 所以即使没有类级事务也能工作；但**派生删除方法（如 deleteByIdAndUserId）不自带事务**，
 * 它只是把实体查出来执行 em.remove()，没有事务时不会 flush，
 * 等到 OpenEntityManagerInView 关闭 EntityManager 时才抛 TransactionRequiredException，
 * 表现就是“删除接口 500，而且记录没删掉”。所以写操作统一加 @Transactional。
 */
@Service
@Transactional(readOnly = true)      // 类级默认：查询走只读事务
public class RecordService {

    @Transactional                    // 写操作覆盖为可写事务
    public RecordResponse create(String username, CreateRecordRequest request) { ... }

    @Transactional
    public RecordResponse update(String username, Long id, CreateRecordRequest request) { ... }

    @Transactional
    public void delete(String username, Long id) {
        Long userId = requireUserId(username);

        if (!recordRepository.existsByIdAndUserId(id, userId)) {
            throw recordNotFound();
        }

        // 派生删除会先查出实体再 em.remove()：keywords/photos 是 @ElementCollection，
        // Hibernate 会先删 record_keywords / record_photos 再删 records，外键约束不会报错。
        recordRepository.deleteByIdAndUserId(id, userId);
    }
}
```

要点：

1. **类级 `@Transactional(readOnly = true)`**：查询方法默认只读，语义清楚，也避免误写；
2. **写方法单独 `@Transactional`**：一个业务操作一个事务，校验 + 落库要么都成功要么都回滚；
3. **不需要改 Repository，也不需要给数据库加 `ON DELETE CASCADE`**：有了事务，Hibernate 会自动按“先子后父”的顺序执行。

## 4. 附带修复：异常不能吞

文件：`backend/src/main/java/com/earthonline/backend/common/GlobalExceptionHandler.java`

```java
@ExceptionHandler(ResponseStatusException.class)
public ResponseEntity<ApiErrorResponse> handleStatus(ResponseStatusException exception) {
    int status = exception.getStatusCode().value();
    String message = exception.getReason() == null ? defaultMessage(status) : exception.getReason();
    // 4xx 属于正常的业务拒绝，记一行 warn；5xx 记完整堆栈，方便线上排障
    if (status >= 500) {
        log.error("请求处理失败 status={} reason={}", status, message, exception);
    } else {
        log.warn("请求被拒绝 status={} reason={}", status, message);
    }
    return ResponseEntity.status(status).body(error(status, "REQUEST_FAILED", message));
}

@ExceptionHandler(Exception.class)
public ResponseEntity<ApiErrorResponse> handleUnexpected(Exception exception) {
    // 以前这里把异常直接吞掉：线上只看到 500，日志里查不到原因，排障无从下手。
    log.error("未预期的服务器异常: {}", exception.getMessage(), exception);
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(error(500, "INTERNAL_ERROR", "服务器暂时无法处理请求，请稍后重试"));
}
```

> 这条改动的价值在本次排查中立刻体现：修好日志之后，验证阶段有一次 UPDATE 返回 500，日志直接打出
> `JSON parse error: Unexpected character ('d')`，一眼看出**是测试脚本把请求体传坏了**，而不是接口的问题。
> 在此之前，同样的 500 只会留下一句“服务器暂时无法处理请求”。

**安全约定**：堆栈只写日志，响应体仍然只给用户一句笼统提示，不泄漏内部实现细节。

**排查经验（也是踩过的坑）**：

- 用 shell 脚本调接口时，**不要让中文出现在 `curl -d '...'` 里**——经 SSH/PowerShell 传输后编码可能被破坏，会得到 `JSON parse error` 这种假故障。写成文件（`--data-binary @file`）或用 `\uXXXX` 转义最稳；

## 7. 答辩问答（可以直接背）

**Q1：为什么只有删除接口 500，新增、修改、查询都正常？**  
> 因为新增/修改走的是 `SimpleJpaRepository.save()`，查询走的是只读查询方法，它们本身就带事务或不需要事务；而删除用的是我在 Repository 接口里声明的**派生方法** `deleteByIdAndUserId(id, userId)`，它不会继承内置方法的 `@Transactional`，而 Service 层当时也没声明事务，于是 `em.remove()` 在没有事务的情况下执行。

**Q2：没有事务时 `em.remove()` 会怎样？**  
> 它只是把实体标记成“待删除”放进持久化上下文，**不会立刻发 SQL**。因为项目开启了 OpenEntityManagerInView，EntityManager 一直活到请求结束；关闭时才尝试 flush，此时没有事务，就抛 `TransactionRequiredException`，最终变成 500，而数据库里什么都没删。

**Q3：为什么加了 `@Transactional` 就能删掉，而且不会撞外键？**  
> `records` 的子表 `record_photos`、`record_keywords` 上有指向 `records(id)` 的外键（没有 `ON DELETE CASCADE`）。在一个事务里，Hibernate 会按“先删子表、再删主表”的顺序把 SQL 发出去并提交，所以既删得掉也不会违反外键约束。

**Q4：`@Transactional` 应该加在 Controller、Service 还是 Repository？**  
> 加在 **Service**。Controller 只负责收请求、做参数校验；Repository 是数据访问层，Spring Data 已经给内置方法配好了事务；业务事务边界属于 Service —— 一个业务操作（校验 + 写库 + 推送）要么全成功要么全回滚。查询方法用 `@Transactional(readOnly = true)`，语义更明确、也利于优化。

**Q5：为什么 `GlobalExceptionHandler` 里一定要打日志？**  
> 因为统一异常处理会把异常“收口”，如果不在那里记录，异常堆栈就彻底消失了，线上只能看到一句笼统的 500 提示——本次排障一开始就是卡在这里，日志里什么都查不到。正确做法是：**堆栈写日志，响应体只给用户安全、笼统的提示**，两边分开。

**Q6：这类问题怎么提前避免？**  
> 三条：① Service 层写操作一律显式声明 `@Transactional`，不要依赖“某个内置方法恰好自带事务”；② 统一异常处理必须记录堆栈；③ 验收不能只看接口返回码，要回到数据库确认主表与子表状态一致（本次就是靠 `record_left=0 / keyword_left=0 / photo_left=0` 才确认删干净了）。

## 8. 经验总结

1. **“报错但没生效”通常不是权限或云服务器的问题**，先看服务端日志；而如果日志里什么都没有，先修“日志”，再修“功能”。
2. **事务边界是 Service 层的职责**；派生查询方法（`deleteByXxx`）与内置方法（`save`/`delete`）在事务上的待遇不同，这是 Spring Data JPA 的常见陷阱。
3. **`@ElementCollection` 的子表 + 外键**决定了删除必须在一个事务内完成，顺序由 Hibernate 保证。
4. **`spring.jpa.open-in-view=true` 会把问题推迟到请求收尾**，报错信息（`TransactionRequiredException`）出现的位置和根因位置并不在一起，看日志要连起来读。
5. **统一异常处理器是“可观测性”的关键位置**：吞异常等于把线上变成黑盒。
6. **验证要落到数据层**：接口 200 + 数据库主/子表零残留 + 关键日志无异常，三条都满足才算修好。
