# 地球动态：新闻数据与实时更新方案

> 文档状态：功能规划，暂不进入开发  
> 适用项目：Earth Online  
> 目标：记录新闻数据的来源、处理流程、实时推送方案，以及后续实现时需要学习的知识点。

## 1. 功能目标

“地球动态”希望展示最近发生的全球新闻，并在有新内容时及时更新页面。完整功能可以分成两个层次：

1. **页面实时更新**：用户正在浏览“地球动态”时，页面提示“发现 N 条新动态”。
2. **系统通知推送**：用户没有停留在页面时，浏览器仍可以推送重大新闻通知。

现阶段项目以学习为主，功能复杂度较高，因此先保留规划文档。后续建议先实现稳定的新闻采集和存储，再实现实时推送。

## 2. 新闻数据从哪里来

项目本身不生产新闻，需要从第三方新闻数据服务、RSS 或公开数据集获取新闻的标题、摘要、发布时间、来源和原文链接。

### 2.1 GDELT

当前项目已经接入 GDELT Doc API，可以作为第一阶段的主要数据源。

特点：

- 覆盖全球大量媒体，适合“地球动态”的全球新闻定位。
- 可以按关键词、时间范围和语言搜索新闻。
- 通常不需要为基础查询配置 API Key。
- 返回结果可能存在重复、噪声、分类不准确等问题，需要自行清洗。
- 它更接近全球媒体监测数据，不是已经整理好的中文新闻产品。

当前代码位置：`server/news-server.js`。

### 2.2 NewsAPI

当前后端也预留了 NewsAPI 接入，通过 `NEWS_API_KEY` 配置。

特点：

- API 结构清晰，适合学习接口调用和数据标准化。
- 可以获取头条或按关键词搜索。
- 开发套餐通常存在调用次数、使用场景或生产环境限制，正式使用前要检查最新套餐规则。
- 返回的正文通常不完整，页面应跳转到新闻来源网站阅读原文。

它适合作为 GDELT 的补充来源，而不建议成为项目唯一的数据源。

### 2.3 RSS/Atom

许多媒体、政府部门、科研机构和国际组织提供 RSS/Atom 订阅源。例如可以选择：

- 联合国及其下属机构；
- NASA、ESA 等科研或航天机构；
- 气候、地震、公共健康等官方机构；
- 明确允许聚合展示的新闻网站。

特点：

- 技术简单，适合边学边做。
- 一般包含标题、摘要、发布时间和原文链接。
- 不同网站的格式和更新频率不一致。
- 使用前需要确认服务条款、版权要求和抓取规则。

RSS 很适合作为第二个学习数据源：先接入少量可靠来源，再逐渐扩展。

### 2.4 其他可选来源

以后还可以考虑：

- 官方开放数据 API：地震、气象、灾害、公共健康等；
- 媒体或内容聚合平台提供的商业 API；
- 经过授权的数据集；
- 自建采集器。

不建议在学习项目早期直接编写通用网页爬虫。网页结构经常变化，而且还涉及 robots.txt、服务条款、版权、反爬措施和数据合规问题。

## 3. 推荐的数据源策略

### 学习和演示阶段

建议使用：

```text
GDELT（主要来源） + NewsAPI（可选） + 本地 Mock 数据（降级）
```

这与当前项目实现基本一致，不需要立刻引入更多服务。

### 功能完善阶段

建议使用：

```text
GDELT + 少量官方 RSS/API + 数据库持久化
```

官方 RSS/API 可以提高特定分类的可靠性，例如：

- 气候与灾害；
- 科技与航天；
- 公共健康；
- 全球经济与国际组织动态。

### 正式上线阶段

需要重新评估：

- 数据源是否允许生产环境使用；
- API 调用额度和费用；
- 是否允许存储标题、摘要和图片；
- 原文链接和来源署名要求；
- 数据源的稳定性、覆盖范围和更新延迟。

## 4. 新闻处理流程

第三方接口返回的数据不能直接展示，后端需要经过统一处理：

```text
新闻 API / RSS
      ↓
定时采集
      ↓
字段标准化
      ↓
去重与内容清洗
      ↓
分类、地区和重要度判断
      ↓
保存到数据库
      ↓
REST API 提供列表
      ↓
SSE 通知页面有新数据
```

建议统一为以下新闻结构：

```js
{
  id: '稳定的内部 ID',
  externalId: '数据源文章 ID',
  title: '新闻标题',
  summary: '简短摘要',
  source: '来源名称',
  sourceUrl: '原文地址',
  imageUrl: '图片地址',
  category: 'climate | science | society | economy',
  region: '国家或地区',
  language: '语言',
  publishedAt: '原文发布时间',
  collectedAt: '项目采集时间',
  importance: 0
}
```

## 5. 为什么需要数据库

当前项目使用内存缓存，服务重启后数据会消失。真正的持续更新需要数据库保存已采集新闻。

数据库主要用于：

- 判断一条新闻是否已经采集过；
- 按时间、分类和地区查询；
- 支持分页和历史新闻；
- 保存用户的订阅、已读状态和推送记录；
- 避免多个用户重复触发外部新闻请求。

项目规划中已经选择 Prisma。学习阶段可使用 SQLite，部署时再切换 PostgreSQL。

去重可以按以下顺序实现：

1. 原文 URL 完全相同；
2. 数据源和文章 ID 相同；
3. 规范化标题后生成的指纹相同；
4. 后期再学习相似文本或事件聚类。

## 6. 实时更新方案

### 6.1 第一阶段：定时轮询

前端每隔几分钟请求：

```http
GET /api/news?category=all
```

优点是实现简单，适合学习阶段。当前项目已经采用这种方式，每 10 分钟刷新一次。

缺点是没有新新闻时也会发出请求，而且更新不够及时。

### 6.2 第二阶段：SSE 页面推送

当后台采集到新新闻后，通过 SSE 通知在线浏览器：

```http
GET /api/news/stream?category=climate
```

SSE 适合该项目，因为数据主要是从服务器单向发送给浏览器。前端可以使用浏览器原生 `EventSource`，不必一开始就引入 WebSocket。

推荐交互：

```text
发现 3 条新动态，点击查看
```

不要在用户阅读时突然重排新闻列表。用户点击提示后，再将新新闻插入顶部。

### 6.3 第三阶段：Web Push

如果希望用户关闭页面后仍能收到重大新闻，需要：

- Service Worker；
- Notifications API；
- Push API；
- VAPID 密钥；
- 后端保存浏览器 Push Subscription。

Web Push 应当由用户主动开启，并提供分类、地区、关键词、免打扰时间和通知频率设置。普通新闻只更新页面，只有重要新闻才发送系统通知。

## 7. 建议的后续实现顺序

### 阶段 A：整理当前功能

- 保留 GDELT 和可选 NewsAPI；
- 修复和完善数据标准化；
- 使用稳定 ID，不把数组下标放入新闻 ID；
- 加强超时、错误处理和 Mock 降级；
- 保持现有 10 分钟轮询。

### 阶段 B：持久化新闻

- 学习 Prisma 基础；
- 创建 News 数据表；
- 编写定时采集任务；
- 实现数据库唯一约束和去重；
- 将 `/api/news` 改成查询数据库；
- 实现游标分页。

### 阶段 C：页面实时更新

- 学习 SSE 和 `EventSource`；
- 新增 `/api/news/stream`；
- 实现心跳和断线重连；
- 增加“发现 N 条新闻”提示；
- SSE 不可用时退回定时轮询。

### 阶段 D：用户订阅和系统推送

- 用户选择关注的分类、地区和关键词；
- 保存订阅规则；
- 实现 Service Worker 和 Web Push；
- 增加重要度阈值、去重和推送频率限制；
- 增加已读状态和通知中心。

- 多来源字段标准化；
- URL 规范化；
- Hash 指纹；

- 用户通知授权和退订机制。

## 9. 第一版建议

等项目的用户系统和数据库基础完成后，再开始该功能。第一版推荐采用：

```text
GDELT
  + 可选 NewsAPI
  + Prisma
  + SQLite（学习阶段）
  + 后端每 3～5 分钟采集
  + 前端 SSE 页面提示
  + 轮询降级
```

暂时不实现 Web Push、复杂爬虫、AI 摘要和多媒体事件聚类。先保证新闻能够稳定采集、正确去重、保存和展示，再逐步增加实时能力。
